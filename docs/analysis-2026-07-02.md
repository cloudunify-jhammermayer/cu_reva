## Findings — High

### H1. Main PR-review path is not nonce-fenced — the injection guard is forgeable
`reva/claude_code_runner.py:228-236` — bug/security

Task parameters (`pr_body`, `diff`, …) are wrapped in **fixed, predictable** XML tags:
`f"<{k}>\n{v}\n</{k}>"`. A PR author can place a literal `</pr_body>` (or `</diff>`
inside a committed file that appears in the diff) followed by fake "Task Parameters" /
instructions and break out of the fence. The codebase's own correct pattern — per-call
`secrets.token_hex(8)` nonce delimiters — is used in `finding_verifier` (SECU-6) and the
ticket paths (SECU-5), but the highest-volume attacker-facing path uses static tags. The
CLI tool allowlist limits blast radius, but injected instructions can suppress/fabricate
findings and poison the check-run verdict.

### H2. Shared repo clone is never force-cleaned before checkout — wedged repos and cross-PR contamination
`reva/claude_code_runner.py:195` (+ `_scrub_clone` at :400-414; unscoped `Write` noted at `worker/worker/runner.py:255`) — bug/security

`ensure_repo` runs plain `git checkout <sha>` (no `-f`/`reset --hard`/`clean`) on the
head-SHA path, while `_scrub_clone` deletes tracked files (`CLAUDE.md`, `.claude/`, …)
after every checkout, and the CLI has an unscoped `Write` tool. Verified empirically:
(a) a modified tracked file that differs between SHAs aborts checkout → `PermanentError`
→ **every subsequent review of that repo fails** until cache eviction; (b) a modified
file identical between SHAs is silently carried into the next PR's review — the tree read
by the reviewer/verifier ≠ the head SHA (cross-PR contamination). Untracked files written
by the CLI accumulate forever. The `head_sha=None` (audit) branch already uses
`reset --hard` and self-heals; the review branch doesn't.

### H3. Explicit re-review recovers its own stale PR review — fresh findings are never posted
`worker/worker/runner.py:394-411`, `reva/db/writers.py` (`reset_review_run_post_state`, `get_review_run_created_at`) — bug

On `/review` re-runs, `reset_review_run_post_state` clears `review_id`, but the recovery
path then searches for `marker="Run #{run_id}"` with `since = created_at - 5min` — and
`created_at` is the **reused row's original** timestamp (never updated by claim/reset).
The first attempt's PR review was posted after `created_at`, so recovery always finds it
and the new PR review is silently skipped (only the Check Run refreshes). Downstream,
`_backfill_comment_ids` then pairs the *new* finding rows positionally against the *old*
review's comments, corrupting the finding↔comment map that comment replies and delta
thread-resolution depend on. The unit test passes only because the fake returns `None`
from `find_pr_review_id` (`worker/tests/test_runner.py:88-89`). The PR-9 comment claims
the `since` guard fixes this exact case; it only fixes the prior-era-row case.

### H4. Deleted/binary/rename-only diff sections bypass every scope filter
`reva/diff_utils.py:135-147` (`filter_diff`), `:165-167` (`filter_diff_by_paths`) — bug/security

Both functions extract the path only from `^\+\+\+ b/(.+)$`; when it doesn't match
(`+++ /dev/null` for deletions, binary files, pure renames) the section is kept
**unconditionally**. Verified empirically: a deleted `odoo/core/*.py` section passes
`filter_diff` untouched. Breaks the "odoo//enterprise/ always stripped" invariant,
bypasses `include_prefixes` scoping and per-repo `skip_paths`, wastes tokens, and widens
H1's injection surface (removed lines of any deleted file reach the model). Fix shape:
read `^--- a/(.+)$` when the `+++` side is `/dev/null`.

### H5. Prod Redis (the RQ broker) runs `allkeys-lru` with no persistence — queued jobs can be silently destroyed
`docker-compose.prod.yml:248` (dev: `docker-compose.yml:133`) — ops/bug

`redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru` on the same DB 0 that RQ
uses as broker. Under memory pressure Redis may evict RQ queue lists/job hashes —
silently dropping enqueued reviews/ticket jobs. No volume and no AOF/RDB on the prod
redis service, so a restart loses every queued job. The stale-`running` reaper only
recovers rows that *started*; `consumed=True` pending_reviews whose job vanished are
never re-enqueued (see M13). Broker DB should be `noeviction` + persisted (split cache
into another DB/instance if LRU is wanted).

### H6. Stuck `pending` ticket analysis wedges the record permanently — no stale-pending escape hatch
`api/app/routes/v1/ticket_analyses.py:150` (requeue 409 gate), `:60-69` (submit dedup); `reva/db/writers.py:1061-1078` — bug

Submit dedups on any `status == "pending"` row with no age bound, and requeue rejects
non-terminal rows with 409. If the RQ job is lost without a terminal DB write (SIGKILL,
Redis flush — see H5), the row stays `pending` forever: every future submit from Odoo
returns the dead `analysis_id` and ops cannot requeue. The sibling feature already
learned this: `ticket_issues.py:214-218` has `_is_stale_pending()` (30-min window) for
exactly this reason. No scheduler reaper covers `ticket_analyses`.

### H7. Ticket analysis is enqueued without `rq.Retry`, but the runner's error contract assumes retries
`worker/worker/ticket_runner.py:42-44, 57-67`; `api/app/routes/v1/ticket_analyses.py:92-96, 167-171` — bug

On `TransientError` the runner re-raises "so RQ will retry" and deliberately does not
record failure — but both enqueue sites pass only `job_timeout`, no `retry=`. One
transient Claude/network blip permanently strands the analysis (DB row pending forever →
H6; Odoo UI pending forever). The completed-but-callback-transient path persists the HTML
then re-raises into the void — result exists in Postgres, Odoo never receives it, nothing
retries.

### H8. Fresh production deploy fails: runbook omits the 5th required secret
`docs/setup-production.md:97` vs `docker-compose.prod.yml:271-281` — docs/usability

The runbook says "All **four** [secrets] are required" and never creates
`./secrets/reva_secret_key`, but the prod compose declares five file-backed secrets and
both api and worker mount `reva_secret_key` — Compose errors out on a missing file.
`.env.example`'s prod-secrets block also lists only four. Only a comment in the compose
header mentions it.

### H9. TUI: `r` on the Odoo tab rotates a live API key — every other tab uses `r` for refresh, no confirmation
`tui/internal/ui/odoo.go:98-107` (refresh remapped to `R` at :117) — usability

A muscle-memory refresh press irreversibly invalidates a production Odoo instance's
callback credentials (old key dead immediately; new key shown once). Needs a confirm
step or a different key.

### H10. Failing tests committed on `main`
`worker/tests/` — quality/process

See baseline above: 3 stale expectations from commits 590fb28 and 55c049b. "Definition of
done" in CLAUDE.md (touched-service suites green before committing) was not followed for
those two commits. Cheap fix; matters because a red baseline masks new regressions.

## Findings — Medium

### Cost / budget integrity
- **M1. Two paid-Claude paths invisible to the budget cap** — `worker/worker/runner.py:737-816` (delta-resolution: up to 20 paid `verifier.is_resolved()` calls per delta review, no `claude_spend` row) and `worker/worker/reviewer.py:505`-ish (a `PermanentError` from `_parse_tool_use` after a full paid CLI run records no spend). Both under-count the rolling 24-h cap.
- **M2. `estimate_cost` pricing keyed on exact alias strings** — `reva/cost.py:44-56`. The Messages API echoes dated model IDs, which miss the table and silently fall back to Sonnet rates (~40% undercount for Opus). Prefix matching would fix it.
- **M3. Comment-reply cost uses hardcoded `"claude-sonnet-4-6"`** while `chat()` uses `default_model` (now `claude-sonnet-5`) — `worker/worker/runner.py:819-900`. Rates coincide today; drift risk. Replies are also enqueued without `retry=` — one 429 silently drops a developer's question (`api/app/routes/webhooks.py:329-339`).

### Retry / error-contract inconsistencies (four runners, four contracts)
- **M4. `PermanentError` in ticket-issue jobs IS retried by RQ** — `worker/worker/ticket_issue_runner.py:200-209`; enqueued with `Retry(max=3)` and re-raises `PermanentError` after recording failure + sending the failed Odoo callback → up to 3 doomed re-runs, each re-sending the callback. `worker/tasks.py`'s swallow-wrapper exists precisely to prevent this, but only wraps reviews.
- **M5. `subprocess.TimeoutExpired` escapes `ClaudeCodeRunner.review()` unconverted** — `reva/claude_code_runner.py:261-281`. Docstring promises only `PermanentError`/`TransientError`; a >1500 s CLI run raises raw `TimeoutExpired`, which the worker's generic handler records as `error_class="permanent"` — an undocumented fall-through, not a decision.
- **M6. GitHub secondary rate limits misclassified as `PermanentError`** — `reva/_github_http.py:31-36`. Only `x-ratelimit-remaining == "0"` is treated as transient; secondary/abuse 403s (with `Retry-After`) permanently fail a review a retry would have completed.
- **M7. GraphQL errors silently swallowed (or crash on nulls)** — `reva/github_client.py:638-662`. Errors arrive as HTTP 200 + `errors[]`; neither `get_review_threads` nor `resolve_review_thread` checks them. `"data": null` → `AttributeError`; nulled sub-object → silent no-op (a missing App permission would never surface).

### Concurrency / lifecycle
- **M8. Per-repo flock held across the whole CLI run defeats `REVIEW_JOB_TIMEOUT`** — `reva/claude_code_runner.py:67-80, 121-142`; `worker/worker/reviewer.py:495-500`. Job B on the same repo can block ~30 min on the unbounded `LOCK_EX`, then start its own 25-min paid run → SIGKILL mid-review — exactly the "can't happen" failure the 1800 s buffer comment rules out. Busy repos degrade to serialized reviews with kill-and-retry churn.
- **M9. Budget-declined (or any declined) explicit re-review destroys the prior completed run's findings** — `worker/worker/runner.py:269-293`; `record_review_declined` upserts the same (repo,pr,sha,mode) row to `declined` and `_replace_findings(run.id, [])` deletes the completed findings. Open inline threads lose their `github_comment_id` backing; delta-base selection changes.
- **M10. Ticket-analysis submit race has no unique-index backstop** — `api/app/routes/v1/ticket_analyses.py:60-99`. Check-then-insert with no partial unique index on pending rows and no `IntegrityError` recovery (contrast `ticket_issues`' `idx_ticket_issue_runs_pending` + recovery branch). Double-click → two paid jobs.
- **M11. Redelivered-while-in-flight webhook can double-process** — `reva/db/writers.py:619-628` + `api/app/routes/webhooks.py:329-339`. The recorded-but-unprocessed row is deliberately handed out for crash recovery, but `_handle_review_comment`'s bare `enqueue` is non-idempotent → two paid reply jobs. Narrow window.
- **M12. Poller enqueues to Redis inside the open DB transaction** — `scheduler/scheduler/poller.py:97-140`. Commit-fails-after-enqueue (or kill between) → `consumed=False` with the job already in Redis → sequential duplicate; `manual_requeue`/`comment` triggers bypass both dedup layers → second paid review. Docstring ("never double-enqueues on restart") overstates. FOR UPDATE row lock is also held across the Redis round-trip.
- **M13. Consumed-but-never-ran reviews have no automated recovery** — `scheduler/scheduler/poller.py:120-134`. Once `consumed=True` commits, the review exists only in RQ; if Redis loses it (see H5) the reaper never sees it (sweeps `review_runs` only). Visible as "queued" in the TUI, but recovery is manual.

### Scalability / data growth
- **M14. `github_events` grows without bound, storing every full webhook payload as JSONB** — written from `api/app/routes/webhooks.py:86-94`; no purge anywhere (ticket text has one — SECU-8 — raw payloads don't). Becomes the largest table within months; also a data-minimisation inconsistency.
- **M15. Unindexed leading-wildcard `ILIKE` full scans on every issue webhook** — `reva/db/writers.py:1367-1375` (`update_ticket_issue_state` materializes full rows incl. `analysis_html` for all historical runs of a repo); same pattern in `purge_old_ticket_issue_text` (:1421-1433) which re-loads already-stripped rows daily, forever.
- **M16. Budget check full-scans an unbounded, unindexed `claude_spend` ledger under a global advisory lock at every job start** — `reva/db/writers.py:331-357`; no `created_at` index, no retention. Also: the lock is released before the paid call, so CLAUDE.md's "checked under an advisory lock" overstates what it protects.

### Ops / deployment
- **M17. `deploy.sh` health verification is dead code and always reports success** — `scripts/deploy.sh:24` uses `curl` inside the api image, which doesn't have curl (that's why the compose healthcheck uses a python one-liner). All 12 attempts fail, then it prints "Deploy complete." and exits 0 regardless.
- **M18. Dev compose exposes the unauthenticated internal/admin API on 0.0.0.0** — `docker-compose.yml:24-25` (`"8080:8080"`), while postgres/redis in the same file are deliberately loopback-only. Dev sets no `REVA_API_KEY` → paid-action endpoints (`requeue`, `audit`, `odoo-instances`) LAN-reachable. Should be `127.0.0.1:8080:8080`.

- **M20. Prod worker has no healthcheck** — nginx/api/scheduler all have one; a worker whose RQ loop is hung stays "Up" indefinitely. The scheduler's heartbeat-file pattern would transplant directly.

### Review pipeline correctness
- **M21. Diff size guards run before `skip_paths`, making the post-filter re-check dead code and its advice wrong** — `worker/worker/reviewer.py:377-411`. Step 7 declines on size before step 8 applies `skip_paths`, so `skip_paths` can never rescue an oversized diff, yet the (unreachable) message tells users to add skip_paths patterns.
- **M22. Fork-PR head SHAs are unreviewable** — `reva/claude_code_runner.py:192-195`. `git fetch origin` never fetches `refs/pull/*`; every fork PR → checkout `PermanentError` → failed run + operator alert. Fine for internal-only, but unguarded and undocumented.

### TUI
- **M23. Failures and Pending tabs clip the detail panel and position line when the list is full** — `tui/internal/ui/failures.go:107-179`, `pending.go:89-154`. Table budget `h-5` + 8-line detail panel + 3 more lines → `h+9`; the `MaxHeight` clamp cuts from the bottom exactly when there are many failures. The overflow test only asserts ≤ terminal height, so this passes CI.
- **M24. Stale review-detail race** — `tui/internal/ui/reviews.go:150-179`; `reviewDetailLoadedMsg` carries no ID, handler assigns unconditionally — holding `j` can leave the pane showing review N-2 for cursor row N.

- **M26. Reviews filter promises "repo or author": author filtering is dead code and repo match is exact-equality** — `reviews.go:39-52`; server side `Repository.full_name == repo` (`api/app/queries/reviews.py:44`) — substring queries return empty with no explanation.
- **M27. Adding a tab touches ~10 hardcoded places in `app.go`**, and the `/`-filter state machine + list scaffold are triplicated (`findings.go:84-99`, `repos.go:121-138`, `tickets.go:277-293`). A `tab` interface + shared filter component would collapse it.

### Docs
- **M28. `FEATURE_ROADMAP.md` asserts in present tense that shipped features don't exist** — lines 13-30: "nothing ever writes a row" to `review_feedback` (written at `webhooks.py:385`), `prompt_versions` "never written" (written at `writers.py:415-435`), delta reviews "re-emit near-identical comments" (delta suppression shipped in v1.6). `HANDOFF.md` points at this as authoritative.
